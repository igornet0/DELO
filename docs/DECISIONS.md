## 1. Принятые архитектурные решения (ADR)

Эти решения следуют из технического задания или безальтернативны для его требований. Пересматриваются только новым ADR.

| ADR | Решение | Основание |
|---|---|---|
| ADR-001 | Модульный монолит на Rust (Cargo workspace, один бинарь `delod` с режимами `serve`, `worker`, `migrate` и `all`) | Требование ТЗ. Микросервисы на старте умножают операционную сложность без выгоды. Границы модулей проводятся крейтами, поэтому модуль можно выделить позже |
| ADR-002 | Слои domain → application → infrastructure внутри модуля. Домен не зависит от БД и HTTP | Тестируемость бизнес-логики без инфраструктуры |
| ADR-003 | Любое действие выполняется от имени `Actor` (User, Agent{run_id}, System, Integration) в `CompanyScope`, который создаётся только после проверки членства | Единая точка для RBAC, аудита и изоляции. Агент не может «стать» пользователем |
| ADR-004 | Любой вызов инструмента агентом проходит Policy Engine (Allow, RequireApproval или Deny). Согласование привязано к `payload_hash` | Требование ТЗ к контролю действий агентов. Защита от подмены аргументов после согласования |
| ADR-005 | Доменные события пишутся в outbox (`domain_events`) в той же транзакции, что и изменение | Нет потерянных и фантомных событий без распределённых транзакций |
| ADR-006 | Деньги хранятся как целые minor units с валютой. Учёт ведётся двойной записью, проводки append-only, баланс проверяется триггером БД | Точность и неизменяемость финансовых данных |
| ADR-007 | Application-слой принимает `&mut PgConnection` как единицу работы | Атомарность межмодульных use case'ов. PostgreSQL — единственное хранилище, поэтому собственная абстракция UnitOfWork не окупается. Подробнее в [ARCHITECTURE.md](ARCHITECTURE.md) |

## 2. Решения, требующие подтверждения

Для каждого решения указаны рекомендация, альтернативы и момент, к которому решение нужно принять. Блокирующие этап 1 отмечены 🔴.

### D-01 🔴 Модель мультиарендности — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** общая схема, колонка `company_id` во всех арендаторских таблицах, составные FK `(company_id, id)` против межкомпанийных ссылок.
- **Альтернативы:** schema-per-tenant (сложные миграции на тысячах схем); database-per-tenant (дорого, оправдано только для крупных корпоративных клиентов).
- **Последствие:** изоляция обеспечивается кодом и RLS (D-03). Выделенная БД для отдельного клиента остаётся возможной позже через отдельную инсталляцию.
- **Срок:** до начала этапа 1.

### D-02 🔴 Целевая версия PostgreSQL — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** PostgreSQL 16+ в production. DDL проверен на 14.17 и не использует возможностей новее 14-й версии.
- **Вопрос к заказчику:** нужна ли совместимость с российскими сборками (Postgres Pro, Jatoba) из-за требований импортозамещения?
- **Срок:** до начала этапа 1.

### D-03 🔴 Row-Level Security как второй уровень изоляции — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** включить. Приложение работает ролью без `BYPASSRLS`, а `app.company_id` устанавливается через `set_config(…, true)` в каждой транзакции.
- **Цена:** небольшие накладные расходы на запросы и дисциплина установки контекста (обеспечивается типом `CompanyScope`).
- **Альтернатива:** только проверки в коде. Тогда одна ошибка в запросе приводит к утечке данных между компаниями.
- **Срок:** до начала этапа 1.

### D-04 🔴 Сессии на непрозрачном токене вместо JWT — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** cookie `delo_session` (`HttpOnly`, `Secure`, `SameSite=Lax`), в БД хранится SHA-256 хеш. CSRF по схеме double-submit (`delo_csrf` и `X-Delo-CSRF`). Для интеграций выдаются API-токены `delo_<prefix>_<secret>`.
- **Почему не JWT:** мгновенный отзыв, отсутствие ключей подписи в обороте и простота. Масштабированию это не мешает: проверка сессии — один индексный запрос.
- **Срок:** до начала этапа 1.

### D-05 🔴 Очередь заданий на PostgreSQL — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** таблица `jobs`, `FOR UPDATE SKIP LOCKED`, аренда через `locked_until`, пробуждение через `LISTEN/NOTIFY`.
- **Альтернативы:** Redis Streams, RabbitMQ, NATS. Это ещё одна система в эксплуатации, и с ними теряется атомарность «изменение + постановка задания».
- **Пересмотр:** при устойчивой нагрузке свыше ~1000 заданий в секунду.
- **Срок:** до начала этапа 1.

### D-06 Redis только при горизонтальном масштабировании — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** в MVP Redis нет, rate limiting работает в процессе. Redis добавляется при запуске второго экземпляра API (распределённый rate limit, кэш).
- **Срок:** до запуска второго экземпляра.

### D-07 🔴 Матрица системных ролей — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Предложение:** роли и разрешения из [API_SPECIFICATION.md §4](API_SPECIFICATION.md#4-разрешения-rbac). Матрица хранится как seed, а код проверяет только разрешения, поэтому изменить её можно без изменения кода.
- **Вопросы к заказчику:**
  - Может ли «Администратор» видеть финансы или это только «Владелец» и «Финансист»?
  - Нужна ли роль «Наблюдатель» (только чтение всего) для инвесторов и аудиторов?
  - Кто вправе повышать лимиты расходов агентов?
- **Срок:** до начала этапа 1 (seed ролей входит в этап 1).

### D-08 Российские LLM-провайдеры и размещение данных — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** на этапе 3 сделать адаптеры Anthropic и OpenAI-совместимый (он же покрывает локальные vLLM и Ollama). Отдельные адаптеры YandexGPT и GigaChat сделать, если подтверждено требование работы с ними.
- **Вопросы к заказчику:**
  - Допустима ли трансграничная передача данных компаний во внешние LLM (152-ФЗ, ст. 12)?
  - Нужен ли режим «только локальная модель»?
- **Срок:** до начала этапа 3.

### D-09 Семантический поиск (pgvector) после MVP — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** в MVP только полнотекстовый поиск PostgreSQL с русской морфологией. pgvector и порт `EmbeddingProvider` подключить после MVP. Схема `kb_chunks` к этому готова.
- **Срок:** до начала этапа 4.

### D-10 Интеграция с 2А — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** тип коннектора `two_a` зарезервирован, но адаптер не пишется, пока заказчик не предоставит официальную спецификацию API 2А (протокол, аутентификация, модель данных, тестовый стенд). Предположений об API 2А в коде нет.
- **Нужно от заказчика:** документация API 2А и доступ к тестовому окружению.
- **Срок:** до начала этапа 6.

### D-11 Контракт API: OpenAPI из кода — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** `utoipa` на backend генерирует OpenAPI, а `openapi-typescript` создаёт из него типы frontend. В CI проверяется, что сгенерированные типы актуальны.
- **Альтернатива:** spec-first (ручной YAML). Тогда два источника правды и риск расхождения.
- **Срок:** до начала этапа 1.

### D-12 Хеш-цепочка журнала аудита — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** на этапе 5 добавить `prev_hash` в `audit_log`, чтобы подмена записей обнаруживалась. До этого журнал защищён триггером append-only и правами БД.
- **Вопрос:** нужна ли юридическая значимость журнала (внешняя метка времени, выгрузка во внешнее хранилище)?
- **Срок:** до начала этапа 5.

### D-13 🔴 BoardDo как основа платформы — [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]
- **Рекомендация:** вариант Б из [BOARDDO_INTEGRATION.md](BOARDDO_INTEGRATION.md#5-варианты-использования). Ядро ДЕЛО (этапы 1–2) строится заново. На этапах 3 и 7 модули BoardDo (движок графа, LLM-адаптеры и маршрутизация, политики, резервирование бюджета, журнал идемпотентности, редактор SBDO) переносятся поверх `CompanyScope` и PostgreSQL вместе со своими тестами.
- **Альтернативы:** А — форк BoardDo с доработкой мультиарендности, IAM и PostgreSQL (переписывается весь слой хранения, высокий риск R-06); В — BoardDo как внешний исполнитель через коннектор (противоречит ADR-003 и ADR-004).
- **Не переносится:** Telegram userbot, сборка ProjectHub и AlertWim из GitHub во время работы, песочница Python без контейнера.
- **Вопросы к заказчику:**
  - Остаётся ли BoardDo самостоятельным продуктом или его развитие переходит в ДЕЛО? От этого зависит, как переносить исправления (R-16).
  - Нужна ли агентам ДЕЛО возможность выполнять код? Если да, требуется песочница с контейнерной изоляцией (R-13).
- **Срок:** аудит кода BoardDo — до конца этапа 0; решение — до начала этапа 3. Этапы 1–2 от решения не зависят.

## 3. Реестр рисков

| # | Риск | Вероятность | Влияние | Меры | Где в архитектуре |
|---|---|---|---|---|---|
| R-01 | Неконтролируемые расходы на LLM | высокая | высокое | Лимиты на запуск, агента и компанию. Учёт стоимости до и после вызова. Остановка запуска со статусом `budget_exceeded` | ARCHITECTURE §6 |
| R-02 | Prompt injection через документы, письма и результаты инструментов | высокая | высокое | Недоверенные данные маркируются и отделяются от инструкций. Policy Engine не зависит от текста модели. CRITICAL и FINANCIAL только с согласованием человека | ARCHITECTURE §6 |
| R-03 | Юридическая ответственность за действия агентов | средняя | высокое | Агент не исполняет платежи и не подписывает от имени компании. Все внешние действия проходят через политики и согласования и фиксируются в аудите. Нужна правовая оценка заказчиком | ADR-004, D-12 |
| R-04 | 152-ФЗ: персональные данные и трансграничная передача | высокая | высокое | Решение D-08, возможность локальной модели, размещение БД в РФ, минимизация ПДн в контексте LLM | D-08 |
| R-05 | Недоступность или блокировка зарубежных LLM в РФ | средняя | высокое | Независимость от вендора через порт `LlmProvider`. OpenAI-совместимый адаптер покрывает локальные и российские шлюзы | ARCHITECTURE §6 |
| R-06 | Утечка данных между компаниями | низкая | критическое | `CompanyScope`, составные FK, RLS (D-03), обязательный тест изоляции для каждого ресурса | ARCHITECTURE §5, DATABASE_SCHEMA |
| R-07 | Двойное исполнение побочного эффекта при падении worker'а | средняя | высокое | Идемпотентные ключи вызовов инструментов, checkpoint'ы runtime, аренда заданий | ARCHITECTURE §5–6 |
| R-08 | Недетерминированные тесты из-за LLM | высокая | среднее | CI только на фейковом провайдере со сценарием. Оценка качества — отдельный ручной прогон | DEVELOPMENT_ROADMAP, этап 3 |
| R-09 | Разрастание объёма (scope creep) | высокая | высокое | Жёсткие критерии готовности этапов. Всё сверх критериев уходит в бэклог | DEVELOPMENT_ROADMAP §1 |
| R-10 | Долгая компиляция большого workspace | средняя | среднее | Крейты создаются по мере этапов, `sccache`, умеренное число зависимостей | ADR-001 |
| R-11 | Ограниченный ресурс команды | высокая | высокое | Вертикальные срезы, MVP из 5 этапов, отказ от необязательной инфраструктуры (Redis, брокеры) | D-05, D-06 |
| R-12 | Отсутствие спецификации API 2А | высокая | среднее | Интеграция не планируется до получения спецификации. Ядро от 2А не зависит | D-10 |
| R-13 | Выполнение кода агентом выходит за пределы песочницы и затрагивает данные других компаний | средняя | критическое | Песочница BoardDo (подпроцесс Python) не переносится. Инструмент выполнения кода доступен только после контейнерной или microVM-изоляции | D-13, BOARDDO_INTEGRATION §4 |
| R-14 | Telegram userbot: нарушение условий Telegram, блокировка аккаунтов, обработка ПДн третьих лиц (152-ФЗ) | высокая | высокое | Userbot не переносится. Интеграция с Telegram только через официальный Bot API | D-13, R-04 |
| R-15 | Сборка внешних репозиториев во время работы (ProjectHub, AlertWim) — атака через цепочку поставок | средняя | критическое | Не переносится. Зависимости фиксируются в `Cargo.lock` и проверяются в CI (`cargo deny`, `cargo audit`) | D-13 |
