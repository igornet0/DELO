## 1. Назначение и границы

ДЕЛО — операционная система компании, в которой операционные функции выполняют ИИ-агенты под контролем владельца.
Платформа — **не чат с ИИ**. Центральные объекты — компания, её структура, задачи, деньги, знания и журнал действий. LLM — один из исполнителей внутри этих процессов, а не интерфейс продукта.

Ключевые инварианты, на которых строится архитектура:

1. **Изоляция компаний.** Любые данные принадлежат ровно одной компании (`company_id`). Доступ между компаниями невозможен без явного механизма (в MVP — отсутствует).
2. **Идентифицируемость действий.** Любое изменение состояния имеет актора (`user` / `agent` / `system` / `integration`), причину и цепочку причинности (запрос → задача → запуск агента → шаг → вызов инструмента → согласование).
3. **Агент не обходит политику.** Решение о допуске действия принимает детерминированный код на backend (Policy Engine), а не LLM. Вывод модели — всегда недоверенные данные.
4. **Деньги двигаются только через финансовый модуль.** Агент может только *запросить* платёж; исполнение — после согласования человеком, с ключом идемпотентности.
5. **Ограниченность выполнения.** Каждый запуск агента имеет жёсткие лимиты по шагам, токенам, стоимости, времени, глубине делегирования.
6. **Независимость от поставщиков.** LLM-провайдеры, хранилище файлов, платёжные системы и 2А подключаются через порты (traits) и адаптеры.

## 2. Архитектурный стиль

**Modular Monolith** на Rust (Cargo workspace), один исполняемый файл `delod` с режимами:

| Режим | Назначение |
|---|---|
| `delod serve` | HTTP API (Axum) + SSE |
| `delod worker` | Исполнение фоновых задач: запуски агентов, уведомления, индексация, интеграции |
| `delod migrate` | Применение миграций SQLx |
| `delod all` | `serve` + `worker` в одном процессе (локальная разработка) |

Модули (bounded contexts) — отдельные crates с явными зависимостями. Это даёт проверку границ компилятором: модуль не может использовать то, от чего не зависит. Выделение модуля в сервис в будущем = замена in-process фасада на сетевой клиент; схема БД при этом уже разделена по префиксам таблиц.

Почему не микросервисы: одна команда, неустоявшиеся границы домена, потребность в транзакциях между задачами/агентами/согласованиями. Цена ошибки в границах в монолите — рефакторинг; в микросервисах — распределённые транзакции.

## 3. Слои внутри модуля

Каждый модульный crate устроен одинаково:

```
crates/delo-<module>/src/
├── lib.rs              публичный фасад модуля (что видят другие модули и API)
├── domain/             сущности, value objects, инварианты, конечные автоматы.
│                       Без IO, без sqlx, без tokio. Покрывается unit-тестами.
├── application/        use cases (команды/запросы), проверка прав, порты (traits),
│                       оркестрация транзакций, публикация доменных событий.
└── infrastructure/     реализации портов: PostgreSQL-репозитории (sqlx), адаптеры.
```

HTTP-слой вынесен в отдельный crate `delo-api`, чтобы доменные модули не зависели от Axum.

**Прагматичный компромисс (ADR-007):** application-слой принимает транзакцию `&mut sqlx::PgConnection` как handle единицы работы, чтобы use case мог атомарно изменить данные нескольких модулей (например, «создать задачу + записать аудит + положить событие в outbox»). Domain-слой от sqlx не зависит. Абстрагировать транзакцию за собственным trait UnitOfWork сейчас не окупается: PostgreSQL — единственное целевое хранилище.

### 4.1. Граф зависимостей модулей

Направление стрелки — «зависит от». Циклы запрещены (проверяется Cargo).

```
kernel ◄── все модули
db     ◄── все модули с хранением
audit  ◄── все модули, меняющие состояние

iam ◄── tenancy ◄── org ◄── agents ◄──────────────┐
                     ▲                            │
llm ◄────────────────┼──────────────── runtime ───┤
tools ◄── approvals  │                   │        │
  ▲          ▲       │                   ▼        │
  │          └───────┴──────────────── tasks ◄────┘
  │
tools-builtin ──► tasks, knowledge, finance, crm, org (через фасады)
runtime ──► agents, llm, tools, approvals, tasks, knowledge (только чтение контекста)
finance ──► approvals, crm         (finance НЕ зависит от runtime и agents)
integrations ──► (порты; адаптеры подключаются в delod)
api ──► фасады всех модулей
delod ──► всё (composition root)
```

Ключевое правило: **`finance` не знает об агентах.** Агент взаимодействует с финансами только через инструменты, которые вызывают те же use cases, что и человек, с актором `agent` и обязательным согласованием для операций категории FINANCIAL.

## 5. Сквозные механизмы

### 5.1. Акторы и причинность

```rust
enum Actor {
    User { user_id: UserId },
    Agent { agent_id: AgentId, run_id: RunId },
    System { component: &'static str },
    Integration { connection_id: ConnectionId },
}

struct Causation {
    request_id: RequestId,          // HTTP-запрос или job
    task_id: Option<TaskId>,
    run_id: Option<RunId>,
    run_step: Option<i32>,
    tool_invocation_id: Option<ToolInvocationId>,
    approval_id: Option<ApprovalId>,
    reason: Option<String>,         // обоснование (для агента — из его шага)
}
```

Каждый use case получает `ExecutionContext { actor, company_scope, causation, permissions }`. Аудит и доменные события пишутся с этим контекстом в той же транзакции. Из этого восстанавливается ответ на вопрос «кто, когда, почему».

### 5.2. Multi-tenancy

- Модель: **общая схема, `company_id` в каждой арендаторской таблице.**
- Уровень 1 (основной): application-слой работает только через `CompanyScope`, полученный после проверки членства. Репозитории принимают `CompanyScope` и всегда фильтруют по `company_id`. Тип `CompanyScope` нельзя сконструировать вне `delo-tenancy` (приватный конструктор) — нельзя «забыть» проверку.
- Уровень 2 (защита в глубину): **PostgreSQL Row-Level Security** на арендаторских таблицах. Приложение подключается ролью без `BYPASSRLS`, в начале транзакции выполняет `SET LOCAL app.company_id = ...`. Ошибка в запросе без фильтра вернёт пустой результат, а не чужие данные. **[ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ, D-03]**
- Составные внешние ключи `(company_id, id)` для связей внутри компании: БД физически не позволит задаче компании A сослаться на агента компании B.
- Тесты изоляции: для каждого репозитория — тест «объект компании B недоступен в scope компании A».

### 5.3. Аутентификация

- Пароли: **Argon2id** (параметры OWASP), проверка на утечку — позже.
- Сессии: **непрозрачный токен** (256 бит) в cookie `HttpOnly; Secure; SameSite=Lax`; в БД хранится только SHA-256 хеш. Отзыв мгновенный, список активных сессий доступен пользователю. JWT не используется: нет требований к stateless-проверке, а отзыв JWT сложнее. **[D-04]**
- CSRF: `SameSite=Lax` + обязательный заголовок `X-Delo-CSRF` (double-submit) для мутирующих запросов.
- Восстановление доступа: одноразовые токены с TTL, хеш в БД, ответ API не раскрывает существование email.
- API-токены (для интеграций и CLI): префикс + хеш, scopes, срок действия.
- MFA (TOTP, WebAuthn) — таблица `mfa_factors` заложена, реализация после MVP.

### 5.4. Авторизация (RBAC)

- Разрешения — фиксированный в коде перечень строк вида `<ресурс>.<действие>`: `company.manage`, `agents.read`, `agents.manage`, `tasks.write`, `finance.read`, `finance.approve`, `approvals.decide`, `tools.policy.manage` и т.д. Полный список — в [API_SPECIFICATION.md §4](API_SPECIFICATION.md#4-разрешения-rbac).
- Системные роли: `owner`, `admin`, `manager`, `member`, `accountant`, `viewer`. Компания может создавать собственные роли из того же набора разрешений.
- Проверка — только на backend, в application-слое (`ctx.require(Permission::TasksWrite)?`). Frontend получает список разрешений лишь для отображения.
- `owner` — единственная роль, которая может: удалить компанию, передать владение, менять политику CRITICAL/FINANCIAL, повышать лимиты расходов агентов.

**Права агентов** вычисляются отдельно:
`effective(agent) = grants(agent) ∩ ceiling(company)`, где `grants` — явно выданные агенту инструменты и scopes данных, `ceiling` — максимально допустимое для агентов в этой компании. Агент никогда не получает разрешений `approvals.decide`, `company.manage`, `members.manage`.

### 5.5. Policy Engine для действий агентов

Чистая детерминированная функция в `delo-tools::domain::policy`:

```
decide(tool, input_facts, agent_grants, company_policy, run_state) -> Allow | RequireApproval{reason} | Deny{reason}
```

Категории и политика по умолчанию:

| Категория | По умолчанию | Может ли владелец ослабить | Примеры |
|---|---|---|---|
| READ | Allow | — | поиск по базе знаний, чтение задач |
| WRITE | Allow (внутренние данные компании) | да / может ужесточить | создать задачу, написать документ |
| EXTERNAL | RequireApproval | да, с лимитом частоты и списком доменов/адресатов | отправить email, вызвать внешний API |
| FINANCIAL | RequireApproval | **нет** (в MVP); позже — авто-одобрение в пределах малого лимита | платёжный запрос, изменение бюджета |
| CRITICAL | RequireApproval владельца | **нет** | удаление данных, изменение прав, публикация от имени компании |

Дополнительные правила, применяемые поверх категории:
- **Taint-контроль (защита от prompt injection):** если контекст запуска содержит недоверенные данные (внешний email, веб-страница, загруженный файл от третьего лица), действия EXTERNAL и выше автоматически требуют согласования, даже если политика разрешает их.
- Пороговые суммы, белые списки получателей, лимиты частоты.
- Бюджет запуска/агента/компании исчерпан → Deny.
- Переопределения на уровне агента могут только **ужесточать** политику компании.

Каждое решение записывается в `tool_invocations` вместе с причиной.

### 5.6. Согласования (Human-in-the-loop)

`approval_requests` — единый механизм для любого действия, требующего человека: вызов инструмента, платёжный запрос, изменение бюджета, публикация.

Жизненный цикл: `pending → approved | rejected | expired | cancelled`, затем для approved — `executed | failed`.
- Запрос содержит человекочитаемое описание, точные параметры действия (что именно будет выполнено), обоснование агента, оценку риска, ссылку на задачу и запуск.
- Одобряется **ровно тот payload**, который показан (хеш payload фиксируется; изменение = новый запрос).
- Исполнение после одобрения идёт с ключом идемпотентности; повторное нажатие или повторная доставка job не приводит к повторному действию.
- Запуск агента, ожидающий согласования, переходит в `awaiting_approval` и освобождает воркер.

### 5.7. Аудит

- `audit_log` — append-only: роль приложения имеет только `INSERT`/`SELECT`; триггер запрещает `UPDATE`/`DELETE`.
- Запись: время, компания, актор, действие, объект, до/после (diff, без секретов), causation, IP/UA для пользователей.
- Хеш-цепочка записей (`prev_hash`) для обнаружения подмены — этап 5+ (**[D-12]**).

### 5.8. Доменные события, outbox, real-time

- Use case пишет доменное событие в `domain_events` в той же транзакции (transactional outbox).
- Воркер-диспетчер читает outbox и: обновляет ленту активности, создаёт уведомления, будит зависимые процессы (разблокировка задач по зависимостям, возобновление запуска после согласования).
- Real-time на фронтенд: **SSE** `GET /api/v1/companies/{id}/events/stream`. API-процесс подписан на PostgreSQL `LISTEN/NOTIFY` и транслирует события, отфильтрованные по компании и правам пользователя. WebSocket не требуется: поток односторонний.

### 5.9. Очередь фоновых заданий

**PostgreSQL-очередь** (`jobs`, `SELECT … FOR UPDATE SKIP LOCKED`, аренда с `locked_until`, `LISTEN/NOTIFY` для пробуждения). **[D-05]**

Причины выбора вместо Redis:
- постановка задания атомарна с изменением бизнес-данных (одна транзакция);
- надёжность хранения и восстановление после падения воркера без дополнительной инфраструктуры;
- объём заданий (тысячи/минуту) в пределах возможностей PostgreSQL.

Свойства: экспоненциальные повторы с джиттером, `max_attempts`, dead-letter статус, уникальный `dedup_key`, приоритеты, ограничение параллельности на компанию.

Redis используется для: распределённого rate limiting, кэша, координации нескольких экземпляров API. Для одного экземпляра в MVP достаточно in-process rate limiter — Redis подключается, когда появится второй экземпляр (**[D-06]**).

### 5.10. Секреты

- Секреты платформы (DSN, мастер-ключ, ключи LLM по умолчанию) — только переменные окружения / Docker secrets. `.env` — в `.gitignore`, в репозитории только `.env.example`.
- Секреты компаний (ключи LLM-провайдеров, токены интеграций) — в БД **зашифрованными** AES-256-GCM (envelope encryption: ключ данных на запись, шифруется мастер-ключом `DELO_MASTER_KEY`; версия ключа хранится для ротации). Позже мастер-ключ переносится в KMS/Vault.
- Секреты никогда не попадают в: ответы API, логи (`tracing` с redaction-обёрткой `Secret<T>`), контекст LLM, аудит.

### 5.11. Rate limiting и защита API

- Tower middleware: лимиты на IP и на пользователя; отдельные жёсткие лимиты на `/auth/*`.
- Ограничение размера тела, таймауты запросов, CORS со строгим списком origin.
- Ключ идемпотентности `Idempotency-Key` для мутирующих POST, критичен для финансовых операций (таблица `idempotency_keys` хранит ответ).
- Валидация всех входов на границе API (типизированные DTO + проверки домена).

### 5.12. Наблюдаемость

- `tracing` + JSON-логи; `request_id`, `company_id`, `actor`, `run_id` — поля span'ов.
- Метрики Prometheus (`metrics` + exporter): задержки API, очередь, запуски агентов, токены/стоимость, ошибки провайдеров.
- OpenTelemetry-экспорт трасс — опционально.
- Здоровье: `/health/live`, `/health/ready` (БД, хранилище).

## 6. Платформа агентов

### 6.1. Модель агента

**Агент** — сотрудник компании, занимающий должность в оргструктуре. Конфигурация агента версионируется: каждый запуск ссылается на неизменяемую `agent_version`, поэтому всегда известно, с какими инструкциями, моделью и инструментами было выполнено действие.

| Требование | Где хранится |
|---|---|
| Идентификатор, название, роль, описание | `agents` |
| Системные инструкции, модель, параметры генерации | `agent_versions` (неизменяемые снимки) |
| Набор инструментов и права | `agent_tool_grants`, `agent_versions.data_scopes` |
| Контекст компании | собирается Context Builder'ом из профиля компании, целей, оргструктуры, базы знаний |
| Память | `agent_memories` (долговременная), `agent_run_steps` (рабочая память запуска) |
| История действий | `agent_runs`, `agent_run_steps`, `tool_invocations`, `audit_log` |
| Статус | `agents.status` (active/paused/disabled) + статус текущих запусков |
| Метрики эффективности | `agent_metrics_daily` (задачи, принятые/отклонённые результаты, стоимость, время) |
| Лимиты ресурсов | `agent_versions.limits` + `budgets` агента |

**Шаблоны** (`agent_templates`) — CEO, Business Analyst, CFO, Marketing, Sales, Support, CTO, HR — это данные (seed), а не код. Компания может создать собственный шаблон или агента без шаблона. Код не содержит ветвлений вида `if role == CEO`; различия выражаются инструкциями, набором инструментов и правами. Особые полномочия CEO (распределение задач по подразделениям) — это просто инструмент `delegate_task` с правом назначать на любые подразделения.

### 6.2. LLM Provider Abstraction (`delo-llm`)

```rust
#[async_trait]
pub trait LlmProvider: Send + Sync {
    fn id(&self) -> ProviderKind;
    async fn complete(&self, req: CompletionRequest, cancel: CancellationToken)
        -> Result<CompletionResponse, LlmError>;
    // потоковая генерация — позже, для UI не обязательна
}

pub struct CompletionRequest {
    pub model: ModelName,
    pub system: Vec<SystemBlock>,       // доверенные инструкции
    pub messages: Vec<Message>,         // включая tool_use / tool_result
    pub tools: Vec<ToolSpec>,           // JSON Schema входа
    pub max_output_tokens: u32,
    pub temperature: Option<f32>,
    pub metadata: RequestMetadata,      // company_id, run_id — для учёта, не для провайдера
}

pub struct CompletionResponse {
    pub content: Vec<ContentBlock>,     // text | tool_call
    pub stop_reason: StopReason,
    pub usage: Usage,                   // input/output/cached tokens
    pub provider_request_id: Option<String>,
}
```

Адаптеры (этап 3): **Anthropic Messages API** и **OpenAI-совместимый Chat Completions** (покрывает OpenAI, локальные vLLM/Ollama и ряд российских шлюзов). Отдельные адаптеры YandexGPT / GigaChat — по решению **[D-08]**.

`LlmError` классифицирован: `RateLimited{retry_after}`, `Overloaded`, `Timeout`, `ContextTooLong`, `InvalidRequest`, `Auth`, `ContentFiltered`, `Transport` — runtime решает, повторять ли.

Каталог моделей `llm_models` хранит цену за токены (в микро-единицах валюты) → стоимость каждого вызова вычисляется и записывается в `llm_usage`. Для тестов — `ScriptedProvider` (детерминированные ответы), используется **только в тестах**, не в продуктовой сборке.

### 6.3. Agent Runtime (`delo-runtime`)

**Запуск (run)** — одно выполнение агентом одной задачи. Конечный автомат:

```
queued → running → (awaiting_approval ⇄ running) → succeeded
                                                  → failed
                                                  → cancelled
                                                  → limit_exceeded
```

Цикл выполнения (воркер):

1. Захватить job `agent_run.step`, загрузить run, `agent_version`, задачу. Проверить, что агент активен, компания не на паузе, `cancel_requested = false`.
2. **Context Builder** собирает запрос (порядок важен для защиты от injection):
   1. Платформенные правила безопасности (неизменяемые, доверенные).
   2. Профиль компании, цели, место агента в оргструктуре.
   3. Инструкции агента из `agent_version`.
   4. Задача: описание, ожидаемый результат, критерии приёмки.
   5. Релевантные фрагменты базы знаний и долговременной памяти — **в обёртке «данные, не инструкции»** с указанием источника и уровня доверия.
   6. Предыдущие шаги запуска (с компрессией при превышении окна).
3. **Резервирование бюджета:** оценка стоимости вызова; если превышает остаток бюджета запуска/агента/компании → `limit_exceeded`.
4. Вызов LLM с таймаутом и `CancellationToken`. Запись шага, фактического usage и стоимости.
5. Для каждого `tool_call`: валидация входа по JSON Schema → Policy Engine →
   - `Allow` → исполнение с таймаутом инструмента, запись результата (с ключом идемпотентности `run_id:step:call_index`);
   - `RequireApproval` → создать `approval_request`, перевести run в `awaiting_approval`, завершить job. Решение человека ставит новый job;
   - `Deny` → вернуть модели структурированную ошибку (агент может скорректировать план).
6. Проверки лимитов и зацикливания. Если модель вернула финальный ответ — передать результат в задачу (`submit_result`), задача переходит в `in_review`.
7. Иначе — поставить следующий шаг (новый job), освободив воркер. Каждый шаг — отдельный job, поэтому падение процесса теряет не больше одного шага, а длинные запуски не держат воркер.

**Лимиты запуска** (снимок в `agent_runs.limits`, значения по умолчанию — из версии агента, верхняя граница — политика компании):
`max_steps`, `max_tool_calls`, `max_input_tokens`, `max_output_tokens`, `max_cost`, `max_wall_time`, `max_llm_call_time`, `max_tool_time`.

**Защита от бесконечных циклов:**
- `max_steps` и `max_wall_time` на запуск;
- детектор повторов: одинаковый (инструмент, нормализованный вход) N раз подряд → остановка;
- глубина делегирования (`tasks.delegation_depth ≤ 3` по умолчанию), лимит дочерних задач на задачу, лимит запусков на корневую задачу (`root_task_id`);
- агент не может делегировать задачу самому себе или вверх по цепочке, из которой она пришла (проверка цикла по цепочке `parent_task_id`);
- общий «стоп-кран» компании: `companies.agents_paused = true` останавливает постановку новых шагов и отменяет текущие.

**Отмена:** `POST /runs/{id}/cancel` выставляет `cancel_requested`; воркер проверяет флаг между шагами, а текущий LLM-вызов прерывается через `CancellationToken` (воркер подписан на NOTIFY отмены).

**Повторы и ошибки:** временные ошибки провайдера → повтор шага с backoff (не увеличивая `step_seq`), постоянные → `failed` с сохранённой причиной; ошибка инструмента возвращается модели как результат; паника в инструменте перехватывается и не роняет воркер.

**Параллелизм:** независимые задачи выполняются параллельно разными job'ами. Ограничения: семафор воркера, `max_concurrent_runs` на компанию и на агента (очередь учитывает при выборке).

### 6.4. Взаимодействие агентов

Свободный диалог агентов **запрещён**. Единственные каналы:

1. **Делегирование задачи** (инструмент `delegate_task`): создаёт дочернюю задачу с полями: инициатор, получатель (агент/подразделение/человек), причина, контекст, ожидаемый результат, критерии приёмки, срок. Инициатор ждёт результата как зависимости.
2. **Запрос информации** (инструмент `ask_colleague`): создаёт запись `agent_interactions` типа `question`, которая исполняется как короткий запуск получателя с лимитом шагов, без права дальнейшего делегирования.
3. **Отчёт/эскалация человеку** (инструмент `escalate_to_human`): задача на человека или запрос согласования.

Каждое взаимодействие (`agent_interactions`): инициатор, получатель, причина, контекст, `task_id`, ожидаемый результат, статус, история (через `task_events`). Право инициировать взаимодействие с конкретным подразделением задаётся грантом агента (CEO — со всеми, остальные — по настройке владельца).

### 6.5. Инструменты

```rust
pub trait Tool: Send + Sync {
    fn descriptor(&self) -> &ToolDescriptor;          // key, версия, описание, категория,
                                                      // input/output JSON Schema, лимиты, требуемые разрешения
    fn assess(&self, input: &Value) -> ToolFacts;     // факты для Policy Engine: суммы, адресаты, затрагиваемые объекты
    async fn execute(&self, ctx: ToolContext, input: Value) -> Result<ToolOutput, ToolError>;
}
```

- Реестр (`ToolRegistry`) собирается в composition root; описание инструментов синхронизируется в таблицу каталога для UI.
- Инструмент исполняется с `ExecutionContext` актора-агента → вызывает обычные use cases модулей, где повторно проверяются права. Инструмент не имеет прямого доступа к пулу БД.
- Выход инструмента, содержащий внешние данные, помечается `trust = untrusted` → включается taint запуска.
- MVP-набор (этапы 3–4): `search_knowledge`, `read_document`, `write_document`, `list_tasks`, `create_task`, `delegate_task`, `ask_colleague`, `update_task_status`, `submit_result`, `escalate_to_human`, `read_finance_summary`, `remember` / `recall`. Внешние инструменты (email, web, CRM) — этап 6.
- **Не реализовано, кандидат:** `delo-workflows` — графовые сценарии (узлы-инструменты, ветвления, ожидание согласования) поверх того же `ToolRegistry` и Policy Engine. Источник — движок BoardDo, решение **D-13** не принято; анализ — [BOARDDO_INTEGRATION.md](BOARDDO_INTEGRATION.md#6-влияние-на-архитектуру). До решения крейт не создаётся.

## 7. Остальные модули

### 7.1. Задачи (`delo-tasks`)

- Задача: проект, родитель (подзадачи), зависимости (DAG, проверка циклов при добавлении), приоритет, срок, статус, исполнитель (`user` | `agent` | `org_unit` | `external_contractor`), создатель (актор), ожидаемый результат, критерии приёмки.
- Статусы: `backlog → todo → in_progress → in_review → done`; плюс `blocked`, `cancelled`. Переход в `todo` при закрытии всех зависимостей — автоматический (по событию).
- **Контроль результата:** результат агента не закрывает задачу автоматически. Режим приёмки задаётся на задаче/проекте: `human` (по умолчанию), `reviewer_agent` (результат проверяет другой агент по критериям приёмки, при отклонении — повторный запуск с замечаниями, ограниченное число раундов), `auto` (только для задач, созданных агентами внутри собственной зоны, с низким риском).
- Комментарии, вложения (файлы через `delo-storage`), история изменений (`task_events`), уведомления.

### 7.2. База знаний (`delo-knowledge`)

- Документ → версии (неизменяемые) → фрагменты (chunks) для поиска.
- Полнотекстовый поиск PostgreSQL (`tsvector`, конфигурация `russian` + `simple` для смешанных текстов, `pg_trgm` для нечёткого поиска по названиям).
- Семантический поиск: `pgvector` + эмбеддинги через порт `EmbeddingProvider` — после MVP (**[D-09]**). Схема `kb_chunks` уже допускает добавление колонки.
- Доступ: документ видим участникам по ролям; агентам — согласно `data_scopes` (разделы базы знаний, подразделения). Context Builder запрашивает знания **только в пределах scope агента и релевантные задаче** (top-k поиска по тексту задачи), а не всю базу.
- Источники: загруженные файлы (извлечение текста: txt/md/pdf/docx — по этапам), результаты задач, отчёты агентов (автоматически, с пометкой автора-агента).

### 7.3. Финансы (`delo-finance`)

- **Двойная запись** (journal + entries, сумма проводок = 0 — проверяется отложенным триггером). Это даёт целостный учёт доходов, расходов, остатков и денежных потоков без расхождений.
- Деньги — `i64` в минимальных единицах + код валюты ISO 4217. Никаких `f64`.
- Бюджеты по периодам и статьям; факт считается из проводок.
- **Платёжный запрос** (`payment_requests`) — единственный путь к движению реальных денег: `draft → pending_approval → approved → executing → executed | failed`, плюс `rejected`/`cancelled`. Исполнение — через порт `PaymentGateway`; **в MVP адаптеров нет**, исполнение отмечается человеком вручную («оплачено вне системы») с прикреплением подтверждения. Никакой имитации платежей.
- Защита: уникальный `idempotency_key`; повторное исполнение невозможно (условие перехода статуса в `UPDATE … WHERE status = 'approved'`); лимиты на агента (в день/на операцию); агенту недоступны операции вывода/перевода средств, изменения реквизитов получателей и лимитов.
- Агенты (CFO) получают отчёты и формируют рекомендации и черновики бюджетов, которые утверждает человек.

### 7.4. CRM (`delo-crm`)

Контрагенты (`client`, `supplier`, `contractor`, `partner`), контакты, сделки (воронка) — этап 5–6. В MVP — справочник контрагентов (нужен финансам и задачам).

### 7.5. Интеграции (`delo-integrations`)

- Каркас: `Connector` trait (описание, требуемые scopes, проверка подключения), `integration_connections` (компания, тип, статус, включено/выключено, зашифрованные учётные данные, выданные scopes), `integration_requests` (журнал всех исходящих/входящих запросов: время, направление, endpoint, статус, объём, кто инициировал — без тел с персональными данными по умолчанию).
- Каждая интеграция отключаема (флаг на подключении + глобальный feature flag).
- Инструменты, использующие интеграцию, имеют категорию EXTERNAL и проходят Policy Engine.
- **2А:** только архитектурное место — тип коннектора `two_a` резервируется, но **адаптер не создаётся, пока нет спецификации API 2А** (**[D-10]**). ДЕЛО не зависит от наличия 2А.

## 10. Соответствие требованиям безопасности

| Требование | Механизм |
|---|---|
| Multi-tenancy, изоляция | `CompanyScope`, составные FK, RLS, тесты изоляции |
| RBAC | Разрешения в коде, роли в БД, проверка в application-слое |
| Защита API | Сессии HttpOnly, CSRF, CORS, лимиты размера/времени, валидация DTO |
| Хранение секретов | env/secrets, AES-GCM envelope encryption, `Secret<T>` с redaction |
| Аудит | append-only `audit_log`, causation на каждом действии |
| Rate limiting | Tower middleware; Redis при горизонтальном масштабировании |
| Повтор финансовых операций | `Idempotency-Key`, уникальные ключи, условные переходы статусов |
| Prompt injection | разделение доверенных инструкций и данных, taint-контроль, Policy Engine вне LLM, валидация схем |
| Доступ агентов к инструментам | гранты + потолок компании + категории + согласования |
| Расходы на LLM | бюджеты компании/агента/запуска, предварительное резервирование, учёт стоимости |
| Таймауты, ошибки | таймауты на LLM/инструмент/запуск, классификация ошибок, повторы с backoff |
| Бесконечные циклы | лимиты шагов, детектор повторов, глубина делегирования, стоп-кран |

## 11. Что сознательно НЕ входит в архитектуру первого релиза

- Микросервисы, Kafka, Kubernetes-операторы.
- Собственное обучение моделей.
- Межкомпанийный обмен данными.
- Реальные платёжные интеграции (только порт, исполнение — вручную).
- Автономное управление компанией без людей (этап 7 — только после накопления статистики качества).
- Telegram userbot (вход под личным аккаунтом пользователя): риск блокировки и нарушения ToS, персональные данные третьих лиц (152-ФЗ) — **R-14**. Telegram допустим только как Bot API через `delo-integrations`.
- Исполнение произвольного кода агентов без контейнерной изоляции (**R-13**).
- Сборка и запуск сгенерированных приложений (runtime builds) — **R-15**.
