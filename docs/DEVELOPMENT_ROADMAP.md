## 1. Принципы ведения этапов

1. **Этап завершён только при выполнении всех критериев готовности.** Если остались критические ошибки, следующий этап не начинается.
2. **Нет имитации функциональности.** Нереализованный endpoint возвращает `404`, а нереализованная страница UI показывает явный статус «Будет на этапе N». Моковые данные в production-сборке запрещены.
3. **Каждый этап заканчивается отчётом** в конце этого файла по шаблону из §4.
4. **Вертикальные срезы.** Этап поставляет миграции, backend, API, UI и тесты вместе. Сначала весь backend, а потом весь UI — так нельзя.
5. **Безопасность входит в каждый этап, а не откладывается.** Tenant isolation, RBAC, аудит и идемпотентность входят в критерии готовности каждого этапа, который их касается.
6. **Миграции только вперёд.** Изменение схемы выпущенного этапа делается новой миграцией.

### Общие критерии готовности (Definition of Done) для этапов 1–7

- `cargo fmt --check`, `cargo clippy -- -D warnings` и `cargo test` проходят. В `npm run lint`, `npm run typecheck` и `npm test` нет ошибок.
- Интеграционные тесты идут на реальном PostgreSQL (testcontainers или docker compose), а не на моках БД.
- Для каждого нового арендаторского ресурса есть тест «пользователь компании A не видит и не меняет данные компании B» на уровне API и на уровне RLS.
- Для каждого нового защищённого endpoint есть тест на `403` без нужного разрешения.
- Каждое изменяющее действие пишет запись в `audit_log` (это проверяется тестом).
- OpenAPI обновлён, и типы frontend перегенерированы.
- Секретов в репозитории нет (`gitleaks` в CI).

### Этап 1 — Ядро (Core)

**Цель:** скелет системы, на котором безопасно строить остальные модули.

Backend:
- Cargo workspace. Крейты `delo-kernel`, `delo-db`, `delo-audit`, `delo-iam`, `delo-tenancy`, `delo-notifications` (только in-app) и `delo-api`. Бинарь `delod` с режимами `serve`, `worker`, `migrate` и `all`.
- Конфигурация из переменных окружения и файла, без секретов в коде. Есть `.env.example`.
- Миграции SQLx для §2, §3 и §11 схемы. Две роли БД: владелец миграций и прикладная роль без `BYPASSRLS`.
- `CompanyScope`, установка `app.company_id` в транзакции и RLS-политики (при подтверждении **D-03**).
- Регистрация, вход и выход. Argon2id, сессии на непрозрачном токене (**D-04**), CSRF и управление сессиями.
- API-токены со scopes.
- Компании, членство, приглашения, системные роли (seed по матрице §4.2 API) и пользовательские роли.
- Проверка разрешений в extractor'е Axum. Аудит с записью в той же транзакции.
- Обработка ошибок RFC 7807, `Idempotency-Key`, `If-Match` и курсорная пагинация.
- Rate limiting в процессе, без Redis (**D-06**).
- Очередь заданий на PostgreSQL (**D-05**) с минимальным worker'ом и outbox в `domain_events`.
- Наблюдаемость: `tracing` (JSON-логи), `request_id`, `/health/live`, `/health/ready` и `/metrics`.
- OpenAPI через `utoipa` (**D-11**).

Frontend:
- Vite + React + TypeScript, TanStack Router и Query, Zustand, Tailwind. i18n с русской локалью по умолчанию.
- Страницы: вход и регистрация, выбор компании, создание компании, участники и роли, профиль и сессии, журнал аудита.
- Оболочка приложения с навигацией. Разделы будущих этапов помечены статусом «Будет на этапе N» и не притворяются рабочими.

Инфраструктура:
- `docker-compose.yml` (PostgreSQL, MinIO, приложение) и multi-stage `Dockerfile`.
- CI: fmt, clippy, тесты, сборка frontend и gitleaks.

**Критерии готовности:**
- Общие критерии DoD.
- Интеграционный тест изоляции арендаторов: API и прямой SQL под прикладной ролью.
- Тест: отозванная сессия перестаёт работать сразу.
- Тест: повтор запроса с тем же `Idempotency-Key` возвращает сохранённый ответ, а с другим телом — `409`/`422`.
- Тест: brute-force входа упирается в rate limit.
- Скрипт проверки DDL из этапа 0 перенесён в интеграционные тесты.

### Этап 2 — Организация

**Цель:** компанию можно «собрать», то есть описать её структуру и сотрудников-агентов. Агенты пока не исполняются.

- `delo-org`: подразделения (дерево), должности, иерархия подчинения и смешанные позиции (человек или агент).
- `delo-agents`: CRUD агентов со всеми 14 атрибутами, шаблоны CEO, BA, CFO, Marketing, Sales, Support, CTO и HR, версионирование конфигурации агента.
- `delo-storage`: порт S3, адаптер для MinIO и S3, загрузка через presigned URL, проверка типа и размера.
- UI: оргструктура (дерево и диаграмма), список агентов, карточка агента (конфигурация без запуска) и мастер найма из шаблона.

**Критерии готовности:**
- Общие критерии DoD.
- Нельзя создать цикл в иерархии подчинения (тест на уровне домена и БД).
- Изменение конфигурации агента создаёт новую версию, старая остаётся доступной.
- Кнопки «Запустить» у агента нет или она явно недоступна с пометкой «этап 3».

### Этап 3 — Agent Runtime

**Цель:** агенты действительно работают: думают через LLM, вызывают инструменты и запрашивают согласования.

- `delo-llm`: порт `LlmProvider`, адаптеры Anthropic Messages и OpenAI-совместимый (по **D-08** ещё YandexGPT и GigaChat). Учёт токенов и стоимости, лимиты расходов на агента и на компанию.
- `delo-tools`: реестр инструментов с категориями READ, WRITE, EXTERNAL, FINANCIAL и CRITICAL, Policy Engine (Allow, RequireApproval, Deny) и JSON Schema для аргументов.
- `delo-tools-builtin`: первые инструменты только внутри платформы (чтение задач, поиск по KB и т. п.). Внешних инструментов нет.
- `delo-approvals`: согласования с `payload_hash`, истечением срока и уведомлением ответственного.
- `delo-runtime`: цикл агента как конечный автомат. Ограничения по шагам, токенам, времени и глубине делегирования, защита от циклов, checkpoint'ы и возобновление после падения.
- Контролируемое взаимодействие агентов: сообщения только по разрешённым каналам, с лимитом глубины.
- **Если D-13 принят в варианте B:** `delo-llm` (адаптеры, роутинг, учёт стоимости), Policy Engine и идемпотентность вызовов (`JournalClaim`) переносятся из BoardDo с адаптацией: суммы из `f64` USD — в minor units, хранение — в PostgreSQL под `CompanyScope`, привязка согласований к `payload_hash`. Перенесённый код проходит те же критерии готовности, что и новый; тесты BoardDo не засчитываются автоматически.
- Защита от prompt injection: разделение доверенных и недоверенных данных в контексте, маркировка внешнего контента, запрет на исполнение инструкций из данных.
- Секреты провайдеров хранятся в AES-256-GCM.
- SSE-поток событий (§5 API).
- UI: запуск агента, просмотр хода запуска (шаги, вызовы инструментов, стоимость), очередь согласований, настройки LLM и лимитов.

**Критерии готовности:**
- Общие критерии DoD.
- Детерминированные тесты runtime на фейковом `LlmProvider` со сценарным скриптом ответов. Реальные LLM в CI не вызываются.
- Тест: превышение лимита стоимости останавливает запуск со статусом `budget_exceeded`.
- Тест: цикл делегирования A→B→A прерывается.
- Тест: инструмент категории CRITICAL без согласования не исполняется, а согласование с изменённым payload отклоняется.
- Тест: worker, убитый посреди запуска, не приводит к двойному исполнению WRITE-инструмента.
- Набор регрессионных prompt-injection-кейсов (документ во вложении задачи пытается вызвать инструмент) — все блокируются политикой.

### Этап 4 — Задачи и знания

**Цель:** работа компании идёт через задачи, а агенты опираются на знания компании.

- `delo-tasks`: проекты и задачи с исполнителем-пользователем, агентом или подрядчиком. Статусы, приёмка результата, комментарии и вложения. Назначение задачи агенту создаёт запуск.
- `delo-knowledge`: статьи, документы, версии и полнотекстовый поиск PostgreSQL (`tsvector`, русская морфология). pgvector — по **D-09**.
- Главная страница: активность агентов и блок «требует вашего действия» (согласования, приёмка, ошибки запусков).
- UI: задачи (список и канбан), карточка задачи, проекты, база знаний и главная.

**Критерии готовности:**
- Общие критерии DoD.
- Результат агента не принимается автоматически: задача переходит в `review`, а приёмку делает человек с `tasks.review`.
- Поиск по KB возвращает только документы своей компании (тест).
- Главная собирается из реальных данных. Пустые состояния отображаются как пустые, без демо-данных.

### Этап 5 — BI и финансы

**Цель:** управленческий учёт и контролируемые платежи.

- `delo-finance`: план счетов, двойная запись с инвариантом баланса в БД, бюджеты и заявки на платёж.
- Заявки на платёж проходят согласование. Исполнение только ручное: человек отмечает «исполнено» и прикладывает подтверждение. Платёжных шлюзов нет. Агент может только создать заявку в пределах лимита и никогда не исполняет её.
- `delo-crm`: контрагенты, контакты и сделки (минимум для финансов и продаж).
- Отчёты: ДДС, P&L (управленческий), расходы на LLM по агентам и выполнение бюджетов.
- Хеш-цепочка аудита — по **D-12**.
- UI: финансы (счета, операции, бюджеты, заявки), CRM и отчёты.

**Критерии готовности:**
- Общие критерии DoD.
- Тест: несбалансированная проводка не фиксируется (повтор проверки этапа 0 в CI).
- Тест: агент не может исполнить платёж ни через API, ни через инструмент. Попытка оставляет запись `denied` в аудите.
- Тест: заявка сверх лимита агента отклоняется политикой до создания.
- Деньги хранятся только в minor units, и арифметика с плавающей точкой отсутствует (проверяется clippy-lint'ом `float_arithmetic` в `delo-finance`).

**На этом MVP завершён.** Перед этапом 6 нужен внешний аудит безопасности и нагрузочный тест.

### Этап 6 — Интеграции

- `delo-integrations`: фреймворк коннекторов (OAuth 2.0, webhook'и с проверкой подписи, хранение токенов в секретах).
- Первые коннекторы выбираются отдельно после MVP (кандидаты: почта IMAP/SMTP, Telegram, Google или Яндекс календарь).
- Инструменты категории EXTERNAL поверх коннекторов, всегда через Policy Engine.
- **2А:** адаптер не создаётся, пока нет официальной спецификации API (**D-10**).

### Этап 7 — Автономный режим

- Расширение полномочий агентов на основе накопленной статистики качества (доля принятых результатов и отклонённых согласований).
- Автоматическое утверждение низкорисковых действий по правилам, которые настраивает владелец.
- Плановые запуски (cron) и самостоятельная постановка подзадач в пределах бюджета.
- Неизменные ограничения: FINANCIAL и CRITICAL никогда не исполняются без человека, и агент не выводит средства.
- Кандидат (по **D-13**): `delo-workflows` — графовые сценарии на основе `Executor`/`NodeRegistry` BoardDo и визуальный редактор SBDO. Исполнение кода только в контейнерной песочнице (без сети по умолчанию, лимиты CPU/памяти/времени); subprocess-песочница BoardDo не переносится (**R-13**).

## 3. Риски плана

| Риск | Влияние | Мера |
|---|---|---|
| Этап 3 значительно сложнее остальных | срыв сроков MVP | начинать с одного провайдера и 3–5 встроенных инструментов, а runtime тестировать на фейковом LLM |
| Разрастание объёма (scope creep) | MVP не выходит | всё, что не входит в критерии готовности этапа, переносится в бэклог следующих этапов |
| Время компиляции workspace из 20 крейтов | медленная разработка | крейты создаются по мере появления этапов, а не все сразу; `sccache` в CI |
| Ресурс команды | параллельная работа над backend и frontend невозможна | вертикальные срезы, страницы UI только для готового API |
| Недетерминированность LLM | нестабильные тесты | CI только на фейковом провайдере; оценка качества — отдельный ручной прогон |
| Перенос кода BoardDo (D-13) | скрытые допущения однотенантной SQLite-модели попадают в ДЕЛО | аудит до этапа 3; перенос по модулю, с адаптацией под `CompanyScope` и minor units; каждый модуль проходит DoD этапа (**R-16**) |

Полный реестр архитектурных рисков ведётся в [DECISIONS.md](DECISIONS.md#3-реестр-рисков).

- Спроектирована схема БД: 61 таблица, RLS, инварианты двойной записи и append-only аудита.
- Спроектирован HTTP API: соглашения, endpoint'ы 17 модулей с этапами появления, перечень разрешений, матрица ролей и SSE.

**3. Принятые решения**
ADR-001 – ADR-007 приняты в рамках этапа 0. Двенадцать решений (D-01 – D-12) ждут подтверждения, см. [DECISIONS.md](DECISIONS.md).

**4. Тесты и результаты**
- DDL из `DATABASE_SCHEMA.md` **реально выполнен** на PostgreSQL 14.17 во временной базе и проверен 10 сценариями: баланс проводок, append-only, межкомпанийные FK, CHECK исполнителя и RLS под ролью без `BYPASSRLS`. Все прошли, подробности в [DATABASE_SCHEMA.md §13](DATABASE_SCHEMA.md#13-проверка-ddl). Временная база удалена.

**5. Что не сделано**
- Не написано ни строки кода: ни backend, ни frontend, ни миграций. Это ожидаемо для этапа 0.
- Проверка DDL — разовая ручная. В автотесты она переносится на этапе 1.
- Не подтверждены решения D-01 – D-12.
- Целевая версия PostgreSQL не зафиксирована. Проверка шла на 14.17, для production рекомендуется 16+.

**6. Проблемы**
- Спецификации API 2А нет, поэтому интеграция с 2А заложена только как зарезервированный тип коннектора.
- Юридические вопросы (152-ФЗ, ответственность за действия агентов) требуют решения заказчика и юриста. Архитектура даёт для них технические механизмы, но не заменяет правовую оценку.

**7. Следующий этап**
Этап 1 — Ядро. Начинается после подтверждения как минимум D-01 – D-05 и D-07.
