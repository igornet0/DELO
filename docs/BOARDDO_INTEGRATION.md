# ДЕЛО — BoardDo как основа платформы

> **Статус: Этап 0, анализ.** Документ отвечает на вопрос, может ли BoardDo стать основой ДЕЛО. Итоговое решение вынесено в [DECISIONS.md, D-13](DECISIONS.md#d-13--boarddo-как-основа-платформы--требует-подтверждения) и ждёт подтверждения.
> Связанные документы: [ARCHITECTURE.md](ARCHITECTURE.md), [DEVELOPMENT_ROADMAP.md](DEVELOPMENT_ROADMAP.md), [DECISIONS.md](DECISIONS.md).

**Источник фактов.** Анализ сделан по локальной копии репозитория BoardDo (`DELO/BoardDo`, версия 0.2.5, лицензия MIT, автор igornet0 — тот же владелец, что и у ДЕЛО). Утверждения с пометкой «проверено» подтверждены чтением исходного кода, пути даны относительно корня BoardDo. Утверждения с пометкой «по README» взяты из описания проекта и **требуют аудита кода**.

---

## 1. Краткий вывод

BoardDo — зрелый однопользовательский движок агентных workflow: граф узлов, исполнитель, LLM-адаптеры, бюджеты, политики, идемпотентный журнал инструментов, визуальный редактор (SBDO). Это ровно та часть, которая в ДЕЛО запланирована на этапы 3 и 7 и считается самой рискованной.

При этом BoardDo не содержит того, на чём стоит ядро ДЕЛО: мультиарендности, PostgreSQL, пользователей и ролей, бухгалтерского учёта. Эти свойства нельзя «добавить сверху» — они проходят через каждый запрос к БД.

**Рекомендация (вариант Б):** ядро ДЕЛО (этапы 1–2) строится заново по текущей архитектуре. Затем модули BoardDo переносятся в ДЕЛО как библиотеки поверх `CompanyScope` и PostgreSQL. Подробности в [§5](#5-варианты-использования).

## 2. Что такое BoardDo (проверено)

| Область | Как устроено в BoardDo | Где в коде |
|---|---|---|
| Хранилище | Один `SqlitePool`. Схема создаётся при старте через `CREATE TABLE IF NOT EXISTS`. Каталога миграций нет, макросы `query!` не используются | `crates/backend/src/storage/mod.rs` |
| Арендаторы | Колонок компании или арендатора нет. Система однопользовательская | `storage/*.rs` |
| Аутентификация | Статические bearer-токены, сопоставленные со строкой principal. Сравнение SHA-256 дайджестов за постоянное время. Токен владельца из `BOARDDO_API_TOKEN` или файла с правами 0600, прочие из `BOARDDO_API_TOKENS` | `crates/backend/src/auth.rs` |
| Пользователи и роли | Нет пользователей, паролей, сессий, RBAC и CSRF | — |
| Учёт расходов | Учитываются только расходы на LLM, в USD как `f64`. Атрибуция через task-local `LedgerScope`. Строки пишутся в `execution_ledger`, данные в JSON-колонке `data` | `ledger.rs`, `storage/ledger.rs` |
| Бюджеты | Резервирование по худшему случаю до вызова, отказ при превышении лимита | `ledger.rs` |
| Политики | `PolicyDecision { Allow, Deny(String), NeedsApproval { capability } }`. Проверяются kill switch, остановка запуска, дедлайн, `max_actions_per_day` | `agent_runtime/policy.rs` |
| Разрешения инструментов | Выдача прав на инструменты (grants). Полный перечень capability **требует аудита кода** | `storage/tool_grants.rs`, `agent_runtime/tools.rs` |
| Идемпотентность | `JournalClaim { Fresh, Reclaimed, Done(Value), InFlight, FailedUncertain(String) }` — журнал вызовов инструментов, защищающий от повторного побочного эффекта | `storage/tool_journal.rs` |
| Движок | `Executor { registry: NodeRegistry }` обходит граф, события уходят через `EventSink` (WebSocket). Есть модули валидации графа и выражений | `engine/executor.rs` |
| Песочница кода | Подпроцесс Python с проверкой AST и audit hook, таймаут, сторож RSS, `RLIMIT_AS` только на Linux. В коде прямо сказано, что это «не контейнер» | `tools/sandbox.rs` |
| LLM | Адаптеры Anthropic и OpenAI, маршрутизация между моделями | `integrations/anthropic.rs`, `integrations/openai.rs`, `routing.rs` |
| Тесты | Около 489 тестов | `crates/**` |
| Frontend (SBDO) | Около 24,6 тыс. строк TS/TSX, визуальный редактор графов | каталог frontend |

**По README, требует аудита кода:**
- Telegram userbot через TDLib.
- ProjectHub и AlertWim клонируются с GitHub и собираются во время работы.
- RustBrowser на Servo.
- Конвейер веб-исследований с фиксацией происхождения данных (provenance).
- Дерево целей (Objectives).

В корне репозитория BoardDo лежат файлы БД `boarddo.db` и `boarddo-smoke.db`. Перед любым переносом кода их нужно проверить на наличие реальных данных и исключить из репозитория.

|---|---|---|---|
| `delo-core` (Actor, CompanyScope, ошибки) | нет | ❌ строить | Писать с нуля по [ARCHITECTURE §5](ARCHITECTURE.md#5-сквозные-механизмы) |
| `delo-iam` (пользователи, сессии, RBAC) | `auth.rs` — статические токены | ❌ строить | Идея сравнения дайджестов за постоянное время применима к API-токенам ДЕЛО |
| Хранилище, миграции, RLS | SQLite, схема при старте | ❌ строить | Схема ДЕЛО уже описана в [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) |
| `delo-llm` | адаптеры Anthropic и OpenAI, `routing.rs` | ✅ перенести | Привести к порту `LlmProvider`, убрать глобальное состояние, ключи брать из хранилища секретов компании |
| `delo-runtime` (цикл агента) | `engine/executor.rs`, `agent_runtime/*` | 🟡 адаптировать | Добавить `CompanyScope`, checkpoint'ы в PostgreSQL, запуск через очередь `jobs` |
| Policy Engine | `agent_runtime/policy.rs` | 🟡 адаптировать | Добавить категории READ / WRITE / EXTERNAL / FINANCIAL / CRITICAL и привязку согласования к `payload_hash` (ADR-004) |
| Идемпотентность инструментов (R-07) | `storage/tool_journal.rs` | ✅ перенести модель | Модель состояний `JournalClaim` переносится как есть, хранилище — на PostgreSQL |
| Бюджеты LLM (R-01) | `ledger.rs`, резервирование | 🟡 адаптировать | Сумма в целых micro-единицах вместо `f64`, лимиты на запуск, агента и компанию |
| `delo-finance` (двойная запись) | нет | ❌ строить | Леджер BoardDo — счётчик расходов на LLM, а не бухгалтерия. В ДЕЛО он остаётся только метрикой использования |
| Workflow и визуальный редактор | движок графа, SBDO | ✅ перенести | Новый модуль `delo-workflows` (см. [§6](#6-влияние-на-архитектуру)) |
| Песочница кода | `tools/sandbox.rs` | ❌ не использовать как есть | Для нескольких арендаторов нужна изоляция контейнером или microVM (R-13) |
| Веб-исследования | конвейер с provenance (по README) | 🟡 после аудита | Кандидат в инструменты категории READ |
| `delo-integrations` | Telegram userbot, ProjectHub, AlertWim (по README) | ⛔ не переносить | Userbot нарушает условия Telegram и создаёт риски 152-ФЗ (R-14). Сборка из GitHub во время работы — риск цепочки поставок (R-15) |
| `delo-tasks`, цели | дерево Objectives (по README) | 🟡 после аудита | Сравнить с моделью задач ДЕЛО |
| Frontend | SBDO, React/TS | 🟡 частично | Брать редактор графа как компонент. Оболочку, авторизацию и маршрутизацию делать по [ARCHITECTURE §8](ARCHITECTURE.md#8-frontend) |

Легенда: ✅ переносится почти без изменений, 🟡 переносится с переработкой, ❌ отсутствует или непригодно, ⛔ сознательно не переносится.

## 4. Разрывы, которые нельзя закрыть настройкой

1. **Мультиарендность.** Во всех таблицах BoardDo нет `company_id`. Чтобы её добавить, придётся переписать каждый запрос, каждый ключ и каждый индекс, а также ввести RLS. По объёму это сопоставимо с написанием слоя хранения заново.
2. **SQLite → PostgreSQL.** Схема создаётся в рантайме без версионирования. ДЕЛО требует версионированных миграций (`sqlx migrate`), проверяемых на этапе компиляции запросов, `FOR UPDATE SKIP LOCKED` для очереди и триггеров для append-only таблиц.
3. **IAM.** Модель «токен → строка principal» не выражает членство в компании, роли и разрешения. Нет сессий браузера и CSRF.
4. **Деньги.** `f64` USD недопустим для финансовых данных (ADR-006). Для метрики расходов на LLM допустим только после перевода в целые единицы.
5. **Песочница.** Ограничения процесса без контейнера не защищают одну компанию от кода, сгенерированного агентом другой компании.
6. **Внешние подключения.** Userbot и сборка чужого кода во время работы противоречат требованиям безопасности ТЗ.

## 5. Варианты использования

### Вариант А — форк BoardDo и доработка
- **Плюсы:** работающий продукт с первого дня, сохраняются 489 тестов и SBDO.
- **Минусы:** переписывать слой хранения, аутентификацию и все запросы под арендаторов. Пока переделка идёт, система находится в смешанном состоянии, и тесты BoardDo не проверяют изоляцию. Велик риск пропустить запрос без `company_id` (R-06). Вместе с кодом наследуются userbot и сборка во время работы.
- **Оценка:** не рекомендуется.

### Вариант Б — новое ядро ДЕЛО и перенос модулей BoardDo (рекомендуется)
- Этапы 1–2 ДЕЛО выполняются по текущей архитектуре.
- На этапе 3 вместо написания runtime с нуля переносятся модули BoardDo: движок графа, журнал инструментов, LLM-адаптеры и маршрутизация, резервирование бюджета, политики. Каждый модуль переносится вместе с его тестами и адаптируется к `CompanyScope` и PostgreSQL.
- Редактор SBDO переносится как компонент frontend, когда появляется модуль workflow.
- **Плюсы:** ядро с изоляцией с первого дня, при этом переиспользуется самая трудная агентная часть. Перенос идёт по модулю, каждый со своими тестами.
- **Минусы:** две кодовые базы расходятся. Исправления в BoardDo придётся переносить вручную (R-16).

### Вариант В — BoardDo как отдельный продукт и коннектор
- ДЕЛО обращается к инсталляции BoardDo через API как к внешнему исполнителю workflow.
- **Плюсы:** минимум работы сейчас.
- **Минусы:** BoardDo однопользовательский, значит нужна отдельная инсталляция на каждую компанию. Аудит, политики и бюджеты ДЕЛО не видят, что происходит внутри. Противоречит ADR-003 и ADR-004.
- **Оценка:** допустим только как временное решение для внутреннего использования.

## 6. Влияние на архитектуру

- **Новый модуль `delo-workflows`** (планируемый, не реализован): хранение графов workflow в PostgreSQL в рамках компании, исполнитель на основе `engine/executor.rs` из BoardDo. Каждый узел, вызывающий инструмент, проходит Policy Engine ДЕЛО. Запуск идёт через очередь `jobs`, события — через outbox и SSE вместо прямого WebSocket.
- **`delo-llm`** строится на адаптерах BoardDo.
- **`delo-runtime`** берёт модель `JournalClaim` для идемпотентности и резервирование бюджета.
- **Песочница кода** выносится в отдельный компонент с контейнерной изоляцией. До его появления инструмент выполнения кода агентам недоступен.

Таблицы для `delo-workflows` в [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) пока не описаны. Они проектируются после подтверждения D-13.

## 7. Влияние на план разработки

| Этап | Изменение при варианте Б |
|---|---|
| 0 | Добавляется аудит кода BoardDo (см. [§8](#8-что-нужно-до-решения)) |
| 1–2 | Без изменений: ядро, IAM, организация строятся по текущей архитектуре |
| 3 | LLM-слой, политики, бюджеты и журнал инструментов переносятся из BoardDo вместо написания с нуля. Ожидаемое сокращение этапа требует оценки после аудита |
| 4–5 | Без изменений |
| 6 | Telegram userbot, ProjectHub и AlertWim не переносятся. Нужные интеграции делаются через официальные API |
| 7 | Модуль `delo-workflows` и редактор SBDO. Песочница кода с контейнерной изоляцией |

## 8. Что нужно до решения

1. Аудит кода BoardDo по пунктам, помеченным «по README» и «требует аудита кода»: перечень capability, конвейер веб-исследований, Objectives, Telegram userbot, сборка ProjectHub и AlertWim.
2. Проверить `boarddo.db` и `boarddo-smoke.db` на наличие реальных данных и секретов.
3. Прогнать тесты BoardDo и зафиксировать фактический результат.
4. Подтвердить, что лицензия MIT и единственный автор позволяют переносить код без ограничений (владелец один, поэтому ожидается да).
5. Решение заказчика по [D-13](DECISIONS.md#d-13--boarddo-как-основа-платформы--требует-подтверждения).
